ReviewMe

Bot de code review par IA : de vrais commentaires inline ligne-par-ligne, un cycle de vie de threads, et plusieurs points d'entrée configurables.

L'essentiel ReviewMe fait reviewer une PR par claude -p, qui produit des findings structurés ; ReviewMe les ancre en commentaires inline sur les bonnes lignes, dédup d'un run à l'autre, et répond dans les threads quand le code évolue. Il se lance en CLI, webhook, poll ou CI. Plusieurs reviewers spécialisés peuvent tourner en parallèle sur une même PR.

Prise en main

Installation

Le moteur d'un côté, votre configuration de l'autre. Trois façons de les relier.

L'essentiel Le moteur est un dépôt, votre instance (projets, personas, .env) en est un autre. En local on garde deux clones ; en CI l'instance monte le moteur en submodule et un seul clone suffit. Pour un seul dépôt à reviewer sans reviewers spécialisés, le mode simple se passe d'instance.

Prérequis

OutilRôle
Python ≥ 3.13Runtime
uvDépendances et exécution (curl -LsSf https://astral.sh/uv/install.sh | sh)
CLI claudeMoteur de review (npm install -g @anthropic-ai/claude-code)
Token GitHubPAT fine-grained Pull requests : R/W, ou une GitHub App
Clé ClaudeANTHROPIC_API_KEY en session non interactive (VPS / CI)

1 · En local : deux clones

git clone <moteur> ~/dev/reviewMe && cd ~/dev/reviewMe
uv sync                                   # + `--extra github-app` pour l'auth GitHub App
npm install -g @anthropic-ai/claude-code

git clone <instance> ~/dev/mon-instance
cd ~/dev/mon-instance
cp .env.example .env                      # GITHUB_TOKEN, GITHUB_REPO, REPO_PATH

./reviewme projects                       # le lanceur trouve le moteur tout seul
PROJECT=mon-repo ./reviewme review --pr 42 --dry-run

Le lanceur cherche le moteur dans REVIEWME_CORE, puis ./.core, puis un clone voisin. S'il ne le trouve pas : export REVIEWME_CORE=~/dev/reviewMe.

2 · En CI : un seul clone

L'instance monte le moteur en submodule .core et épingle sa version — pas de moteur qui change sous les pieds entre deux builds.

# une fois, dans le dépôt d'instance
git submodule add <moteur> .core && git commit -m "add(core) - moteur épinglé"

# en CI
git clone --recurse-submodules <instance> config
cd config && ./reviewme review --pr "$PR_NUMBER"

Aucune variable à poser, et sans .venv pré-construit le lanceur passe par uv run : uv est la seule dépendance à installer. Détails et exemple GitHub Actions : Reviewers & projets.

3 · Sans instance : le mode simple

Un seul dépôt à reviewer, un seul reviewer, pas de personas spécialisées : le moteur se suffit à lui-même.

git clone <moteur> reviewme && cd reviewme && uv sync
cp .env.example .env                      # sans PROJECT ni REVIEWME_CONFIG_HOME
uv run reviewme review --repo OWNER/REPO --pr 1234 --dry-run

La persona vient alors de config/prompts/system.md et les règles de config/guidelines/<pack>/.

Créer une instance depuis zéro

mkdir ~/dev/mon-instance && cd ~/dev/mon-instance && git init
export REVIEWME_CONFIG_HOME=$PWD
~/dev/reviewMe/.venv/bin/python -m reviewme.cli init-project mon-repo --reviewers tech,i18n

Puis ajuster common/*.md (langue, ton), les personas dans reviewers/<id>/system.md, et déclarer les conventions à lire via [context] read. Copier le lanceur reviewme depuis une instance existante rend la commande directement disponible.

Toujours commencer par là Committer le .gitignore en premier, dans les deux dépôts : il protège .env (token) et data/ (contenu de PR réelles). Ne jamais faire git add -A avant.
Premier lancement Toujours en --dry-run : tout est calculé, rien n'est posté. C'est ainsi qu'on calibre le seuil de confiance avant de brancher sur un vrai dépôt.

Guidelines & prompts

Avec un PROJECT, tout vient du projet : la persona (reviewers/<id>/system.md), les consignes communes (common/*.md) et les conventions lues dans le dépôt reviewé ([context] read). Seul config/output-contract.md (le contrat JSON) reste imposé par le moteur — cf. Reviewers & projets.

Comprendre

Fonctionnement

Du diff au commentaire inline, en passant par la validation et la réconciliation.

L'essentiel Le moteur renvoie des findings JSON ; ReviewMe valide chaque ligne contre le diff (sinon 422), dédup par un fingerprint stable, poste tout en un seul write, et répond dans les threads quand une ligne a bougé.

1 · Findings structurés

Le moteur (claude -p, persona config/prompts/system.md) répond par un JSON : summary + liste de findings {path, line, severity, message, snippet, confidence}. Si le JSON est invalide, ReviewMe retombe sur un commentaire global plutôt que de crasher : la review est livrée, en moins bien, jamais perdue.

2 · Validation anti-422

GitHub valide une review de façon atomique : un seul commentaire sur une ligne hors-diff rejette TOUTE la review. diff_utils parse les patches (GET /pulls/{n}/files) et calcule les lignes réellement commentables. Les findings hors-diff sont basculés dans le summary, jamais postés en inline.

3 · Fingerprint & déduplication

Chaque commentaire porte un marqueur invisible <!-- reviewme:REVIEWER:HASH --> où HASH = sha1(path + contenu réel de la ligne) — indépendant du numéro de ligne et du texte narré par le LLM, donc stable entre deux runs. On reconnaît nos commentaires par ce marqueur, jamais par l'auteur (sinon on toucherait les threads humains).

La clé de déduplication est le couple (reviewer, hash). C'est ce qui permet à deux reviewers de commenter la même ligne sans que l'un fasse disparaître l'autre.

Propriété clé Le hash porte le contenu de la ligne, pas son numéro : un commit qui décale le code ne recrée aucun commentaire. Le reviewer_id est un préfixe du marqueur et n'entre pas dans le hash. Verrouillé par tests/test_fingerprint_migration.py.
Piège REVIEWER_ID doit rester stable dans le temps pour un projet donné : le renommer rend orphelins tous les commentaires déjà postés, qui seront alors reposés en double. Même règle que pour le hash.

Changer de moteur LLM

La review est produite par la CLI claude, lancée en sous-processus. Trois niveaux de personnalisation, du plus simple au plus lourd :

BesoinComment
Passerelle d'entreprise
(proxy compatible Anthropic)		Rien à coder : ANTHROPIC_BASE_URL et ANTHROPIC_AUTH_TOKEN dans le .env sont hérités par le sous-processus. Ajouter CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1 si le proxy rejette les en-têtes de prompt caching.
Wrapper maison
(quotas, journalisation, auth)		CLAUDE_BIN=/chemin/wrapper. Le wrapper doit accepter les mêmes arguments et produire la même enveloppe --output-format json.
Un autre modèle
via une API de complétion		Pas une question de configuration — voir l'avertissement ci-dessous.
Ce n'est pas qu'un endpoint claude -p est un agent : il ouvre les fichiers du dépôt, cherche dedans, lit l'historique git pour contextualiser un finding. Une API de complétion classique ne fait rien de tout ça — tout devrait tenir dans un seul prompt. Basculer sur ce type de moteur, c'est un backend à écrire (assemblage du contexte, parsing, comptabilité du coût), pas une variable à poser.

4 · Cycle de vie des threads

SituationAction
Finding nouveauAjouté au batch inline
Finding déjà posté, toujours valideDédup — rien
Finding persiste, commentaire devenu outdated (nouveau commit)Réponse dans le thread existant (pas de doublon)
JSON moteur invalideFallback : commentaire global
422 résiduel sur le batchRepli : tout en commentaire global (rien perdu)

Le batch inline = un seul POST /pulls/{n}/reviews (respecte la limite de 80 créations/min).

Comprendre

Reviewers & projets

Plusieurs relecteurs spécialisés, activés projet par projet.

L'essentiel Un projet = un dossier par repo, qui porte ses reviewers complets (persona incluse) et ses consignes communes. Chaque reviewer a son objectif, ses entrées et son format de sortie. Le projet active ceux qu'il veut ; le diff déclenche ceux qui le concernent.

Pourquoi plusieurs reviewers

Pas pour alléger un prompt trop gros : parce que les entrées et les sorties diffèrent. « AC3 non couvert » n'a aucune ligne de diff à pointer — c'est une absence, pas une erreur située. Un finding technique, si. Les deux ne peuvent pas partager un format de sortie.

ReviewerObjectifEntréesSortieDéclenchement
techArchi, sécurité, perf, fiabilité, conventionsdiff + conventions du repoinlinetoute PR
usLes critères d'acceptation sont-ils couverts ?ticket Jira + diffglobalclé de ticket détectée
i18nComplétude et qualité des traductionsfichiers de locale + diffmixtewhen.paths

Ce sont des objectifs types livrés dans config/templates/, pas des prompts partagés : chaque projet part du squelette puis écrit sa propre persona.

Le modèle : le projet est l'unité

config/
  output-contract.md          ← CORE : interface du parseur, aucun projet ne la redéfinit
  projects/
    ah-ios/
      common/*.md             langue, ton, format — PAS les conventions de code
      reviewers/              ← LA source de vérité : un dossier = un reviewer
        tech/{reviewer.toml, system.md}
        us/{reviewer.toml, system.md}
        i18n/{reviewer.toml, system.md, precheck.py}
    bff-api/
      common/*.md
      reviewers/{tech, us}/   ← une API n'a rien à traduire

La présence du dossier suffit à activer le reviewer : il n'y a aucune liste à tenir à jour ailleurs. Pour en mettre un en sommeil sans supprimer son dossier : enabled = false dans son reviewer.toml.

Pas d'héritage entre projets : deux teams sur deux produits écrivent des personas réellement différentes, même pour un objectif identique. La duplication est le prix assumé de leur indépendance — bornée (une persona ≈ 45 lignes) et amorcée par reviewme init-project.

Effet de bord utile Tout le contenu propre à un projet (personas métier, consignes internes) vit dans un seul dossier — un seul chemin à exclure d'un dépôt public.

Deux niveaux de sélection

1 · Activation
le projet choisit ses reviewers
→
2 · Déclenchement
le diff décide qui tourne
→
3 · Exécution
en parallèle, écriture unique

Le niveau 2 n'est pas un confort. Sans lui, chaque PR paie tous les reviewers activés : à ~0,65-0,91 $ par reviewer, quatre reviewers systématiques coûtent ~3 $ la PR. i18n ne se déclenche que si le diff touche un fichier de localisation ; us que si une clé de ticket est détectée.

Écriture unique et plafond

Les reviewers s'exécutent en parallèle (chacun est un claude -p indépendant), mais l'écriture GitHub passe par un seul point : dédup partagée, limite de 80 créations/minute respectée, et surtout plafond de commentaires calculable — impossible à faire reviewer par reviewer.

Le vrai risque Quatre reviewers zélés = 15 commentaires = le développeur décroche et désactive le bot. MAX_COMMENTS_PER_PR (défaut 10) coupe par PR, tous reviewers confondus, en gardant les plus graves puis les plus sûrs. Le reste est journalisé, pas posté.

Le déterministe avant le LLM

Un reviewer peut déclarer un precheck : un script dont la sortie est injectée comme faits établis. « La clé checkout.title existe en fr et manque en de » est vérifiable — gratuit, instantané, sans faux positif. Le modèle garde ce qui demande du jugement : variables non substituées, pluriels, longueur, ton. Ne jamais payer un LLM pour ce qu'un diff fait mieux.

Les conventions ne se recopient pas

Un projet documente déjà ses règles (AGENTS.md, CONTRIBUTING.md, docs/). En copier le contenu dans la config d'un reviewer crée une copie qui diverge en silence dès la première évolution du repo — et personne ne le voit, puisque le reviewer continue de citer d'anciennes règles avec assurance.

Un reviewer déclare donc ce qu'il faut lire, et le moteur le résout à chaque review :

# reviewer.toml
[context]
read = ["AGENTS.md", "documentations/CODING_STYLE.md", "documentations/"]
DéclaréCe que fait le moteur
un fichierInjecte son contenu — toujours à jour, et l'agent ne peut pas « oublier » d'aller le lire
un dossierInjecte l'inventaire de ses .md ; l'agent ouvre ce qui concerne la PR
un chemin absentWARNING explicite dans les logs
un chemin hors du dépôtRefusé (../, chemin absolu)
Le gain Quand un fichier de conventions est renommé ou supprimé, le WARNING le signale au run suivant. Sans déclaration, le reviewer perdrait ses règles sans que personne ne s'en aperçoive — il continuerait de commenter, simplement moins bien.

Il reste donc dans common/ uniquement ce qui n'existe nulle part dans le repo : langue, ton, longueur des remarques, faux positifs à ne jamais produire — commun à tous les reviewers du projet.

Une instance = un dépôt de config

Une organisation ne veut ni forker le moteur (il faudrait rebaser à chaque évolution), ni committer ses personas et consignes internes dans le dépôt du moteur. La config de projets vit donc dans son propre dépôt, relié par une seule variable :

export REVIEWME_CONFIG_HOME=~/dev/mon-instance

mon-instance/            ← dépôt privé, versionné à part, aucun code moteur
  projects/
    api/                   reviewers/tech/
    webapp/                reviewers/{tech, i18n}/

Le moteur n'étant pas dans ce dépôt, l'instance porte un lanceur ./reviewme qui le localise et lui passe la main — plus son propre .env, qui prime sur celui du moteur (repo cible, token, seuils propres à l'instance) :

./reviewme projects
./reviewme review --pr 147 --dry-run

# équivalent manuel, sans le lanceur :
REVIEWME_CONFIG_HOME=~/dev/mon-instance \
  ~/dev/reviewMe/.venv/bin/python -m reviewme.cli projects

C'est délibérément un chemin, pas un submodule git : un submodule ramène exactement les frictions d'un fork (init, update, HEAD détachée, commit de pointeur à chaque changement) que ce découpage cherche à éviter. Deux dépôts indépendants ; le moteur reste git pull-able sans conflit.

Moteurconfig/templates/Squelette copié par init-project
Dépôt de configprojects/<repo>/reviewers/Personas et consignes communes : propre à l'organisation

En CI : l'instance épingle le moteur

En CI, on ne veut ni deux clones à synchroniser, ni un moteur qui change de version sous les pieds entre deux builds. L'instance monte alors le moteur en submodule .core : elle épingle la version qu'elle utilise, et un seul clone ramène tout.

# dans le dépôt d'instance, une fois
git submodule add <url-du-moteur> .core

# en CI
git clone --recurse-submodules <url-de-l-instance> config
cd config && ./reviewme review --pr "$PR_NUMBER"

Le lanceur détecte .core seul — aucune variable à poser. Sans .venv pré-construit il passe par uv run : rien à installer d'autre que uv. Mettre à jour le moteur devient un geste explicite et daté : git -C .core pull puis commit du pointeur.

Le sens du montage C'est l'instance qui épingle le moteur, jamais l'inverse. Le moteur ne référence aucune instance, reste neutre, et peut être partagé ou publié — alors qu'un moteur qui monterait ses instances en submodules se salirait d'un commit de pointeur à chaque changement de persona.

Agréger plusieurs dépôts de config

Quand plusieurs équipes maintiennent chacune leur config, un dépôt chapeau peut les monter en submodules. Deux conditions :

ConditionDétail
Un submodule = un projetMonté en projects/<repo>, avec reviewers/ et common/ à sa racine. Monter un dépôt qui contient lui-même un projects/ ajoute un niveau : le moteur ne le trouve pas.
Le chapeau n'est jamais le moteurSinon le dépôt du moteur référence des dépôts privés et se salit d'un commit de pointeur à chaque changement de config — précisément ce que la séparation évite.

Git refuse deux submodules au même chemin (already exists in the index), donc un doublon de projet est impossible par construction.

Le coût réel Un git clone sans --recurse-submodules donne des dossiers de projets vides, et un git pull ne les met pas à jour sans git submodule update. Le moteur détecte ce cas et le dit explicitement, mais c'est une friction permanente : ne prendre les submodules que si l'agrégation est un vrai besoin. Pour une seule instance, REVIEWME_CONFIG_HOME suffit.

Créer un projet

reviewme init-project ah-ios --reviewers tech,us,i18n
reviewme projects          # liste les projets et leurs reviewers

# puis, dans .env :
PROJECT=ah-ios

Le dossier porte le nom du repo, jamais celui de l'équipe : une team renommée ou une app qui change de main ne doit rien casser.

Piège L'id d'un reviewer entre dans le marqueur de dédup. Le renommer sur un projet en cours rend orphelins tous ses commentaires déjà postés, qui seront reposés en double.

Architecture

Un noyau unique, plat, config-driven. La logique de review et de posting vit dans le repo.

L'essentiel Layout plat, config-driven. Deux principes : (1) un seul moteur pour toutes les équipes, la config vit ailleurs ; (2) toute la logique de posting est dans ce dépôt, donc auditable — rien n'est caché dans un plugin externe.

Points d'entrée

La même brique run_review(), déclenchée de quatre façons.

L'essentiel Aucune logique de review dupliquée : chaque entrée résout une PR puis appelle run_review(). On choisit l'entrée selon le contexte de déploiement.

CLI (one-shot)

  • reviewme review --repo --pr
  • La brique commune
  • Idéal : CI, cron, test manuel

Webhook

  • Event pull_request → review
  • HMAC obligatoire (fail-closed)
  • Idéal : VPS temps réel

Poll

  • Boucle sur PR labellisées / toutes
  • Aucune exposition entrante
  • Mode legacy / dev

CI

  • GitHub Actions ou Bitrise
  • Appelle le CLI one-shot
  • 1 build = 1 review
Reco Démarrer par le CLI one-shot (rien à exposer, valide toute la chaîne). Passer au webhook pour le temps réel une fois le VPS exposé proprement (TLS + HMAC).
Exploiter

Déploiement

VPS (webhook/poll), Bitrise, ou GitHub Actions.

Quelle que soit la cible, le déploiement clone l'instance (avec le moteur en submodule .core) et appelle son lanceur — cf. Installation § En CI.

Runner Linux, même pour un projet iOS La review ne compile rien : elle lit un diff et des fichiers texte, sans Xcode ni toolchain. Bitrise permet de surcharger le stack par workflow (meta.bitrise.io.stack), donc une app iOS peut avoir son workflow de review sur Linux — bien moins cher à la minute qu'un runner macOS. Exemple complet : deploy/bitrise-step.md.
L'essentiel Recettes prêtes dans deploy/. Le point à trancher au déploiement reste l'auth du moteur en session non interactive : ANTHROPIC_API_KEY, ou une passerelle d'entreprise via ANTHROPIC_BASE_URL.

Sécurité

Le moteur lit du contenu de PR non fiable et poste sur des PR : modèle de menace explicite.

À lire avant tout déploiement Un auteur de PR est non fiable. Sans précautions, le diff peut pousser le moteur à écrire des fichiers (RCE) ou exfiltrer des secrets dans un commentaire public. Les garde-fous ci-dessous sont implémentés ; le sandbox réseau reste à câbler au déploiement.

Garde-fous en place

MenaceMitigation (implémentée)
Écriture arbitraire (injection → RCE)Allowlist verrouillée Read,Glob,Grep,Bash(git log/show/diff) — pas de Write, jamais --dangerously-skip-permissions
Exfiltration de secretsDiff traité comme donnée non fiable ; scrub (tokens, clés, chemins absolus) sur tout texte avant post
Webhook usurpéHMAC X-Hub-Signature-256 en temps constant, corps brut, fail-closed sans secret
Token trop puissantPAT fine-grained, 1 repo, PR R/W (pas de classic repo)
Dashboard exposéCORS * retiré, endpoint d'écriture /api/requeue supprimé, read-only 127.0.0.1
Fuite de secrets/données.gitignore couvre .env et data/
Reste à faire au déploiement La mitigation n°1 de la prompt-injection — exécuter claude -p dans un sandbox sans réseau sortant (hors GitHub) et avec un Read confiné au clone cible — n'est pas gérable dans le code : à câbler au niveau infra (conteneur/systemd + firewall). Le scrub est la dernière barrière, pas la seule.
Identité dédiée Faire tourner le bot sous une GitHub App plutôt qu'un PAT humain : token court renouvelé automatiquement, permissions explicites, et les commentaires arrivent sous <slug>[bot] au lieu du compte d'une personne. Il suffit de renseigner GITHUB_APP_ID et GITHUB_APP_PRIVATE_KEY_PATH.

Statut & limites

Ce qui tourne, ce qui n'existe pas encore, et ce qu'il faut calibrer.

L'essentiel Le cœur est validé sur de vraies PR : commentaires inline ancrés aux bonnes lignes, aucun doublon après un commit qui décale le code, et plusieurs reviewers en parallèle sur un même diff. Restent deux réglages à faire à la main sur chaque dépôt : le seuil de confiance et le plafond de coût.

Validé sur de vraies PR

VérificationRésultat
Inline sur les bonnes lignesOK re-ancrage par le contenu quand le modèle se trompe de quelques lignes
Dédup sur re-reviewOK même commit et commit suivant : zéro doublon
Fan-out multi-reviewersOK deux reviewers en parallèle, une seule écriture GitHub
Déclenchement par le diffOK un reviewer ne tourne que si la PR le concerne
Conventions lues dans le dépôtOK et un chemin obsolète est signalé

À calibrer sur chaque dépôt

RéglagePourquoi
CONFIDENCE_THRESHOLDÀ 80, l'essentiel des findings est filtré sur du code déjà relu. Passer quelques PR en --dry-run et regarder ce qui aurait été posté avant de trancher.
MAX_BUDGET_USDLe coût suit la taille du diff : un gros diff coûte plus cher qu'un reviewer de plus. Le plafond s'applique par reviewer.
MAX_COMMENTS_PER_PRLe facteur d'abandon d'un bot de review est le bruit, pas le manque de findings.

Ce qui n'existe pas

AbsentConséquence pratique
Sandbox de déploiementÀ câbler à l'infra (pas de réseau sortant, FS confiné). C'est la mitigation de fond contre la prompt injection — cf. Sécurité.
REQUEST_CHANGES bloquantLe bot ne pose que des COMMENT. Exige une GitHub App comme identité.
Resolve / unresolve des threadsGitHub replie déjà les commentaires devenus obsolètes.
Commentaires multi-lignes et suggestionsUn finding s'ancre sur une seule ligne, côté droit du diff.
Arrêt net au plafond de coût d'une PRLes reviewers tournent en parallèle : le dépassement est journalisé, pas interrompu.
